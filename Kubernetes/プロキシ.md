結論から言うと：

# ■ 基本動作

以下のように環境変数を設定すると：

```sh

export HTTPS_PROXY=http://proxy.example.com:8080
```

`dnf` / `yum` はこれを参照してリポジトリにアクセスします。

内部的には：

* `libcurl`
* `libdnf`

* 内部通信がプロキシ経由になって失敗
* Oracleのローカル通信が壊れる


| コマンド     | proxy対応   |
| -------- | --------- |
| dnf      | 完全対応      |
| yum      | 対応        |
| microdnf | 対応（ただし簡易） |

* SELinux / 制限環境

* repoがHTTPではなく別プロトコル

# ■ dnf.conf に proxy を追加するスクリプト

```sh
#!/bin/sh
set -e

PROXY_URL="http://proxy.example.com:8080"

DNF_CONF="/etc/dnf/dnf.conf"

# =========================
# dnf.conf が存在するか確認
# =========================
if [ ! -f "$DNF_CONF" ]; then
  echo "dnf.conf が存在しません: $DNF_CONF"
  exit 1
fi

# =========================
# proxy 設定の追加 or 上書き
# =========================

# 既存 proxy 行があれば削除
sed -i '/^proxy=/d' "$DNF_CONF"

# [main] セクションが存在するか確認
if grep -q "^\[main\]" "$DNF_CONF"; then
  # [main] の直下に追加
  sed -i "/^\[main\]/a proxy=${PROXY_URL}" "$DNF_CONF"
else
  # [main] セクションがなければ追加
  echo "[main]" >> "$DNF_CONF"
  echo "proxy=${PROXY_URL}" >> "$DNF_CONF"
fi

echo "dnf proxy 設定完了:"
grep proxy "$DNF_CONF"

# =========================
# 動作確認（任意）
# =========================
# dnf repolist
```

---

# ■ 説明（重要ポイント）

## 1. proxy は `[main]` セクションに書く

```ini

```

これが正しい位置です。

## 2. 既存設定を消してから入れる

基本的には **できません**。
Pod の `env:` は、**Pod 定義に書いた値**、**ConfigMap / Secret**、**Downward API の Pod 情報**などから設定しますが、**ノード（ホストOS）のシェル環境変数をそのまま自動参照する仕組みはありません**。 ([Kubernetes][1])

つまり、次のようなことはできません。

```yaml
env:
  - name: HTTP_PROXY
    value: $HOST_HTTP_PROXY
```

この `$HOST_HTTP_PROXY` を Kubernetes がノードOSの環境変数として解決してくれるわけではありません。`env` は Pod マニフェスト内で明示した値か、`valueFrom` で参照可能な Kubernetes リソースからしか入りません。 ([Kubernetes][1])

使える入力元は主に次です。

* `value:` で固定値を直接書く
* `valueFrom.configMapKeyRef` / `secretKeyRef`
* `envFrom` で ConfigMap / Secret をまとめて取り込む
* `valueFrom.fieldRef` で Pod 名や Namespace などを取る（Downward API） ([Kubernetes][1])

現実的なやり方は、**ホストOSの環境変数をどこかで Kubernetes リソースに変換してから使う**ことです。たとえば:

1. `kubectl` 実行時にシェル展開して YAML/Helm に埋め込む
2. ConfigMap や Secret に登録して `envFrom` / `valueFrom` で読む
3. CI/CD や GitOps でテンプレート変数として注入する ([Kubernetes][1])

例としてはこうです。

```yaml
env:
  - name: HTTP_PROXY
    valueFrom:
      secretKeyRef:
        name: proxy-secret
        key: HTTP_PROXY
  - name: HTTPS_PROXY
    valueFrom:
      secretKeyRef:
        name: proxy-secret
        key: HTTPS_PROXY
```

認証付きプロキシなら、**Secret に入れる**のが妥当です。Secret は Pod の環境変数や Volume として渡せます。 ([Kubernetes][2])

補足すると、Kubernetes は **Service に関する環境変数は自動注入**しますが、これはクラスタ内部の Service 情報であって、ノードOSの一般的な環境変数とは別物です。 ([Kubernetes][3])

結論としては、

> **Kubernetes の `env` からホストOSの環境変数を直接読むことはできない。**
> **使いたいなら、事前に ConfigMap / Secret / テンプレート展開で Kubernetes 側に渡す。**

必要なら、次に **「kubectl でホスト環境変数から Secret を作って Pod に渡す例」** をそのまま使える形で書きます。

[3]: https://kubernetes.io/blog/2025/11/25/configuration-good-practices/?utm_source=chatgpt.com "Kubernetes Configuration Good Practices"
